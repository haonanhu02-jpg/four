# 四层对齐工作台 1.0.1：生产部署与恢复

本说明随当前源码维护。1.0.1 起使用工号与至少 6 位密码登录、注册，不需要邮箱或 SMTP。已有 v1.0.0 发布附件保留发布时的邮箱登录实现和对应文档。

运行包供独立部署，包含 Linux amd64 的 API、web、PostgreSQL 18 镜像归档、源代码归档、配置及验证记录。浏览器正式业务数据保存于 PostgreSQL；访客、本机草稿和离线队列保存于浏览器 IndexedDB。账号数据独立。

## 1. 环境与交付文件

服务端需要 Docker Engine 与 Docker Compose 2.20 或更新版本。配置生成、校验和备份助手使用 Node.js 24；直接运行已打包镜像不需要安装 npm 依赖。源代码开发及测试需要另行解压 `source.tar.gz`，使用 Node.js 24、npm 11 执行 `npm ci`。

| 文件 | 用途 |
| --- | --- |
| `images.tar.gz` | API、web 和 PostgreSQL 镜像，可用 `docker load` 装载 |
| `release.json` | 镜像 ID、固定版本标签、来源指纹、逐源文件和交付文件校验值 |
| `SHA256SUMS` | 归档及配置文件 SHA-256 |
| `source.tar.gz` | 源代码、测试、迁移和工程配置；不含 node_modules、实际密钥或数据库 |
| `compose.production.yaml` | 生产运行配置；支持内置或独立数据库 |
| `deploy/production.env.example` | 脱敏配置模板；归档版本已填本次固定镜像标签 |
| `verification/` | 容量、浏览器、恢复和容器重建验证摘要 |

本次没有 Git 仓库，因此用完整源代码内容的 SHA-256 关联镜像，并写入 OCI revision 标签。以后接入 Git 时，干净工作区可记录提交 SHA；未提交的代码仍以内容指纹标识，不冒充已提交代码。GitHub Actions 配置在源代码中，当前未运行远端工作流或推送镜像。

## 2. 装载、校验及生成配置

在解压后的运行包目录执行：

```sh
node deploy/verify-release.mjs .
docker load --input images.tar.gz
node deploy/verify-release.mjs . --images
node deploy/init-production.mjs
```

初始化只创建新 `.env.production`，不会覆盖现有配置；随机生成数据库密码与账号令牌密钥。没有 Node.js 时，可以手动从 `deploy/production.env.example` 复制配置并生成足够长度的随机密钥。数据库密码使用 URI 安全的随机十六进制字符，并同步填写 `POSTGRES_PASSWORD` 与 `DATABASE_URL`。

填写以下实际配置后启动：

| 配置 | 要求 |
| --- | --- |
| `APP_ORIGIN` | 用户访问的完整 HTTPS 源，例如 `https://workbench.example.com`，不带路径前缀 |
| `COOKIE_SECURE` | 生产为 `true`；仅 localhost 演练允许 HTTP / `false` |
| `API_IMAGE` / `WEB_IMAGE` | 使用运行包给出的固定标签，升级时成对替换 |
| `POSTGRES_IMAGE` | 归档中对应的固定 PostgreSQL 标签；恢复工具也使用该镜像 |
| `DATABASE_URL` | 从容器可访问的 PostgreSQL 地址；内部数据库主机名为 `db` |
| `WEB_BIND_ADDRESS/WEB_PORT` | 默认 `127.0.0.1:8080`，供同主机 HTTPS 反向代理访问 |
| `TRUST_PROXY_HOPS` | 仅应用内 Nginx 为 1；采用本文 HTTPS 代理示例时为 2 |
| `DB_POOL_MAX` | 单 API 实例默认 10；增加实例时累计连接数须计入数据库容量 |

`AUTH_TOKEN_SECRET` 及数据库密码只由环境注入，不写入镜像或提交仓库。应用首次没有默认账号密码，使用工号和至少 6 位密码直接注册；不要求字母、数字或特殊字符的组合，保留 128 位长度上限。工号作为文本保存，保留前导零，去除首尾空白并忽略英文字母大小写。升级迁移保留旧账号的 ID、密码、数据和原登录名，后续再绑定工号。邮箱验证码及邮箱找回密码接口已停用。

## 3. 使用内置数据库启动

```sh
docker compose --env-file .env.production -f compose.production.yaml --profile database up -d --pull never --wait --wait-timeout 180
docker compose --env-file .env.production -f compose.production.yaml --profile database ps
```

`--pull never` 可确认只使用本运行包中已经装载的镜像。首次建立 PostgreSQL 持久卷，等待数据库健康，执行一次性迁移，再启动 API / web。默认不向宿主机暴露数据库端口，API 也仅供容器网络访问。

API 和 web 以非 root 用户运行，禁用额外能力及提权，根文件系统只读；临时目录使用 tmpfs。默认资源上限为 API 2 CPU / 1 GiB、数据库 2 CPU / 2 GiB、web 1 CPU / 128 MiB。健康检查涵盖数据库连接及迁移后可访问性。容量实测的完整主机配置和负载模型见第六阶段验收记录，不将这些上限视为任意服务器的性能承诺。

数据库数据位于 `${COMPOSE_PROJECT_NAME}_postgres_data` 持久卷。停止应用使用 `docker compose ... down`，保留卷。日常升级不使用 `down -v`，不删除或覆盖该卷。

## 4. 使用独立数据库

将 `DATABASE_URL` 改为容器可访问的独立 PostgreSQL 地址，按数据库要求配置 TLS 连接参数，然后不启用 `database` profile：

```sh
docker compose --env-file .env.production -f compose.production.yaml up -d --pull never --wait --wait-timeout 180
```

此时仅运行迁移、API 和 web；不会建立本地数据库服务。迁移账号需有当前数据库的建表、索引和迁移权限。不要同时让应用误连旧库与新库。独立数据库模式已使用另一 Compose 项目的 PostgreSQL 演练；没有把该结果宣称为客户实际云数据库的网络/TLS验收。

## 5. 域名、HTTPS 与安装

按 `deploy/https.nginx.example.conf` 在可信的 HTTPS 反向代理上替换域名与证书路径。示例将请求转给同主机 `127.0.0.1:8080`，覆盖来自客户端的转发地址头，再由应用 Nginx 代理 API。不要在未经信任的多级代理链上随意增加 `TRUST_PROXY_HOPS`。

web 设置安全响应头、页面禁止嵌入及同源 CSP；静态文件长期缓存，入口、manifest 和 service worker 每次检查更新。API 响应不进入离线缓存。业务字段受前后端校验，版本条件和幂等编号保护多端修改。

网页提供系统/浅色/深色三种外观，主题保存在本浏览器。Chrome / Edge 等支持安装提示时显示“安装工作台”；iOS Safari 可从分享菜单添加到主屏幕。安装资源包含 192、512 和 maskable 图标，Chrome 安装资格检查无错误。不同系统的安装交互仍由浏览器控制，安装程序不会绕过用户确认。

新版本的 service worker 等待用户点击“保存并更新”，先检查本机持久化成功，再激活并重开；尚未写入本机时拒绝更新，已持久化的离线队列在重开后继续保留。首次加载需要联网；断网时不执行云端历史查询或跨期操作，恢复网络后补偿。

## 6. 数据库备份

在部署目录运行，网络名应与实际 `COMPOSE_PROJECT_NAME` 对应：

```sh
node deploy/database.mjs backup --env .env.production --network four-layer-workbench-production_default --file backups/workbench-2026-10-22.dump
```

工具使用 PostgreSQL 18 的 `pg_dump -Fc`，创建一致性完整备份及 `.sha256` 校验文件。包含账号、事项、版本、历史快照、排期日志及业务备份，不依赖浏览器 JSON 导出。输出文件已存在时拒绝覆盖；失败的输出保留为 `.partial`，不作为成功备份。密钥通过进程环境传给临时 PostgreSQL 工具容器，不打印到日志。

独立数据库可省略 `--network`，或者指定能访问其地址的 Docker 网络。地址必须从工具容器可达，不能把宿主机 `127.0.0.1` 当作数据库容器地址。

部署后应按业务恢复点要求定时执行备份，并将备份和校验文件复制到独立存储。镜像归档不含数据库；同一宿主机上的数据库卷与备份不能替代异机副本。

## 7. 从备份恢复

恢复工具只允许写入没有业务表的空数据库，先校验 SHA-256，使用 `pg_restore --single-transaction --exit-on-error`。校验失败或目标非空时不执行恢复。

1. 暂停应用写入并另外备份当前数据库；保留现有数据库及旧镜像，确认所选备份时间点。
2. 新建空库。例如默认数据库用户下可执行 `CREATE DATABASE workbench_recovered TEMPLATE template0 OWNER workbench;`。
3. 复制配置为 `.env.restore`，只将 `DATABASE_URL` 改到新库，不覆盖原配置。
4. 执行恢复并核对账号、事项、关联、版本及历史内容：

```sh
node deploy/database.mjs restore --env .env.restore --network four-layer-workbench-production_default --file backups/workbench-2026-10-22.dump
```

恢复完成后，工具撤销备份中的登录会话与验证码，并更换缓存恢复标记。重新启动应用前执行随镜像提供的迁移：旧备份没有该标记表时，由迁移创建。使用者需重新登录；浏览器看到标记变化会重建云端缓存，移除备份中不存在的旧记录，同时保留未提交草稿并要求确认，即使恢复前后事项版本数字相同也不会自动覆盖新恢复的数据。

5. 将应用连接切到新库，启动匹配的 API / web 镜像，完成注册/登录、四层事项、待办勾选、跨期、同步和历史检查，再恢复服务。恢复点之后的已提交业务变更需要另行从其他备份或记录找回，不能由旧备份自动重建。

本次演练对所有账号、四层事项、封存及排期记录计算内容指纹，与恢复结果逐表比较；重新建立应用容器后指纹也一致。会话与缓存标记按设计更换，不纳入“不变”断言。非空恢复与篡改备份的拒绝路径也已验证。

## 8. 升级与回退

升级前备份数据库和当前配置，记录当前镜像 ID。装载新归档并核验后，成对更新 `API_IMAGE` / `WEB_IMAGE`，保留数据库配置、持久卷和已有密钥，再执行启动命令；迁移按文件名及校验和执行，不重复建表。已执行的迁移文件不修改。第六阶段新增 `0004_cache_generation.sql`，其余迁移保持原内容。

应用回退需使用同一版本的前后端，并核对新数据库结构是否仍兼容旧应用。第六阶段新增表为附加结构，但旧版不具备新的缓存恢复处理；数据库恢复后应使用 1.0.0 及以后匹配版本，不能把切回旧镜像当作数据库回滚。涉及不兼容结构时，在新库恢复对应时间点备份，验证后切换连接；保留原库供复核，避免在现有库内盲目反向执行迁移。

## 9. 日志与故障定位

```sh
docker compose --env-file .env.production -f compose.production.yaml ps -a
docker compose --env-file .env.production -f compose.production.yaml logs --tail 100 migrate api web
```

- 健康检查：应用的 `/api/health`，web 的 `/healthz`。API 错误返回请求编号，可与服务端错误日志对应。
- 迁移失败：先看 migrate 日志和数据库连接，不跳过失败迁移直接启动业务。
- 工号无法登录：检查工号和密码是否正确；已有旧账号暂使用原登录名，重复工号不能再次注册。连续错误尝试会触发限流，请稍后重试。
- 401：重新登录。403：核对域名、代理链和账号是否切换。409：处理版本冲突或重新预检批量导入；原本机草稿保留。
- 页面仍是旧版本：使用页面更新入口，确认本机草稿已保存；不要直接清空浏览器存储来处理待同步数据。

## 10. 已知交付边界

本版本为个人目标管理，未实现组织权限、多人共享目标、AI 自动拆解。JSON 单文件导入最多 5 MiB / 10000 条；业务清空或替换前若备份超出可恢复上限，会拒绝执行，先分批整理。历史数据和业务备份按现有规则保留，容量增长需持续监测；不要任意清除服务端幂等回执以处理磁盘空间，旧离线操作仍可能重试。

实际生产域名、证书及远程服务器仍按部署环境配置，应用不依赖邮件服务。历史版本的源码与镜像已发布到 GitHub；当前源码的变更不会替换既有发布附件，镜像来源与校验以具体版本的 `release.json` 为准。

参考：[PostgreSQL 18 备份](https://www.postgresql.org/docs/18/app-pgdump.html)、[恢复工具](https://www.postgresql.org/docs/18/app-pgrestore.html)、[PWA 安装要求](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)。
