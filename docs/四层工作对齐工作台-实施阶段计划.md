# 四层工作对齐工作台：实施阶段计划

状态：已按用户授权在本地完成第一至第六阶段；第六阶段已完成本地验收与交付。GitHub 仓库尚未提供，未操作远程仓库。阶段成果见[第一阶段](阶段1-验收记录.md)、[第二阶段](阶段2-验收记录.md)、[第三阶段](阶段3-验收记录.md)、[第四阶段](阶段4-验收记录.md)、[第五阶段](阶段5-验收记录.md)及[第六阶段验收记录](阶段6-验收记录.md)。

## 1. 已确认范围

- 前端：Vue 3 + TypeScript + Vite。
- 后端：NestJS，使用 TypeScript 编写，编译后由 Node.js 运行 JavaScript。
- 服务端数据库：PostgreSQL，保存正式业务数据。
- 浏览器存储：IndexedDB，承担访客数据、草稿和离线待同步操作；不替代 PostgreSQL。
- 用户规模：约 1000 名使用者；账号数据独立，支持手机和电脑使用。
- 功能：以已确认的年度目标、月度目标、周任务、每日待办、今日概览、对齐体检、周期管理及基础能力为准，保留年度/月度双视图。
- 最终交付：可运行的前后端生产镜像、镜像归档、Compose 配置、数据库迁移与部署文档。
- GitHub 仓库由用户稍后提供；接收后先适配仓库已有结构与规范。

当前交付已覆盖第六阶段。多人共享目标、组织权限、AI 自动拆解等尚未进入本轮范围；已有技术方案中的可安装网页应用作为最后阶段的交付增强。

## 2. 阶段与依赖

实施主线为 1 → 2 → 3 → 4 → 5 → 6。每阶段都交付可运行版本及本阶段验证结果；测试和容器构建从第 1 阶段开始，最后一阶段集中完成生产环境验证与发布包。

每个阶段的数据库变更都提供迁移文件，避免仅修改开发库而无法重现。阶段交付记录包含变更说明、运行方法、验收结果和仍需处理的问题。

### 阶段 1：工程底座、账号与数据规范

做什么：

- 根据提供的仓库建立前端、后端及共享接口类型，配置开发环境、代码检查、构建和持续集成基础。
- 接入 PostgreSQL，创建四层业务表及账号、版本、软删除、原始排期、变更记录和历史快照所需结构。
- 建立登录、退出、账号注册与恢复流程；对原型中的邮箱密码、验证码能力提供统一账号接口及邮件配置方式。
- 落实服务端账号隔离、关联归属校验、统一错误格式、字段校验和健康检查。
- 预先定义版本条件更新、请求幂等与同步错误响应，离线队列在第 5 阶段实现。
- 提供基础 Dockerfile、开发 Compose、环境变量示例和数据库迁移入口。

交付：可启动的工程、账号页面及接口、可迁移的数据库、基础容器构建和运行说明。

验收：前后端能够连接真实 PostgreSQL；完成登录后可访问受保护接口；两个账号的数据互不可见；从空库可执行迁移并启动；基础镜像能够构建。需要外部邮件服务的流程在配置测试环境后验证，不以模拟发送冒充实际邮件可用。

### 阶段 2：四层业务主链与在线保存

做什么：

- 完成年度目标、月度目标、周任务、日待办的前端组件和后端增删改查。
- 实现年→月→周→日关联及完整来源链路展示，允许未关联事项。
- 支持目标说明、年/月手动进度及权重、月目标截止日、周优先级与状态、日日期与预计耗时及完成勾选。
- 完成点击编辑、滑块、选择关联、回车连续新增，以及经 API 自动保存到 PostgreSQL。
- 实现年度/月度视图框架、年/月/周/日选择和自定义跨月区间查询。
- 实现删除父项保留下级、当前关联解除提示及可恢复删除，历史保留来源。
- 页面基础布局兼顾桌面和手机，不将所有响应式处理推迟至最后。

交付：可以在线实际使用的四层工作台。

验收：创建年度目标→拆月目标→拆周任务→排日待办→勾选完成整条链路可走通；刷新和重新登录后数据仍存在；不同账号隔离；自定义区间按已约定的相交规则检索；删除父项不会丢失下级事项。

### 阶段 3：汇总、年度归集与对齐体检

做什么：

- 完成年度进度、月度进度、周推进指数、今日完成率及今日焦点。
- 明确展示年/月手动进度与子任务完成统计，保留首版的独立完成口径。
- 实现年度执行归集，按年度目标分组，区分月/周/日层级和已完成/未完成，历史列表分页。
- 实现四层关联缺失、目标未拆任务、周任务未安排动作等体检规则，提供定位与修复入口。
- 汇总日计划分钟数，显示逾期、未关联以及上层完成而下层未完成等提示。
- 完善空状态、无权重状态及跨区间去重，统一前后端统计口径。

交付：能够看执行进展和定位对齐问题的完整双视图。

验收：示例数量为 4 年度/6 月度/7 周/7 日；对应汇总为 31%/66%/50%/0/7。勾选一条日待办后，当日完成率为 14%、年度归集完成数增加，上层手动进度不被自动覆盖。孤立事项可由体检定位，0 权重处理正确。

### 阶段 4：自动顺延、跨期承接与历史复盘

做什么：

- 实现日、周、月未完成事项的顺延，覆盖自然周期、自定义区间及跨月场景。
- 分别保存原计划、当前排期、截止日、顺延次数与变更历史，周期复盘使用封存快照。
- 跨年保留原年度来源，提示承接确认，允许用户显式选择新年度关联。
- 完成服务端定时处理、访问时补偿、云端恢复及导入后的补偿检查。
- 实现事务、版本条件更新/锁行、顺延唯一约束，防止多端打开或多实例重复执行。
- 日期按用户时区计算，保留进度、优先级和完成状态；查看历史时不强制跳走。

交付：可追溯、可复盘的周期管理功能。

验收：跨天、跨周、月底及跨年用例通过；本周内已经结束的自定义区间能识别过期；已完成事项不顺延；重复请求只产生一次有效变更；顺延后原周期记录、截止日和历史来源仍可查看。

### 阶段 5：浏览器草稿、多端同步与数据迁移

做什么：

- 实现 IndexedDB 访客数据、编辑草稿和持久化待提交队列。
- 登录后的正常业务操作经 API 保存至 PostgreSQL，断网时保存本机操作，联网后有序重试。
- 实现按事项版本处理多端冲突；上传期间继续编辑时，不清除尚未提交的新修改。
- 区分本机已保存、待同步、云端已保存和冲突状态；切回应用或网络恢复后刷新相关数据。
- 隔离访客和各账号缓存，处理首次登录时的本地数据导入及退出/切换账号。
- 实现旧 JSON 预检、导入预览、事务导入、版本化导出、示例加载和清空恢复入口。

交付：手机电脑同步、可离线保留编辑、可迁移旧数据的版本。

验收：离线编辑后关闭再打开仍保留操作；联网重试不重复新增；两端修改不同事项互不覆盖，同一事项冲突可恢复；切账号不串数据；旧示例 JSON 导入后数量与关联不丢失；错误文件不会破坏原数据。

### 阶段 6：生产镜像、容量与最终交付

做什么：

- 完善手机触控、布局、深浅色和关键操作反馈，补齐可安装网页应用资源及相应验证。
- 在约 1000 个账号和长期业务数据下进行容量测试，覆盖集中访问、自动保存、离线恢复与批量顺延。
- 构建前端生产镜像和后端生产镜像；采用多阶段构建，镜像使用固定版本标识并可对应到代码提交。
- 提供生产 Compose：web、api、PostgreSQL；支持通过配置接入独立数据库。数据库使用持久卷，镜像升级不覆盖业务数据。
- 配置健康检查及启动依赖，提供一次性数据库迁移步骤，演练空环境启动和已有数据升级。
- 完成备份恢复、日志定位、配置说明及镜像版本切换的回退说明；应用回退需与数据库结构兼容。
- 结合 GitHub 仓库配置测试与镜像构建流程；镜像仓库及推送方式在提供目标仓库后确定，本计划不触发发布。

交付：前后端可运行镜像及归档文件、Compose、迁移与备份恢复工具、版本说明、部署文档和整体验收记录。

验收：在干净的 Docker 环境中装载/构建镜像并按文档完成数据库迁移和启动；走通登录→四层拆解→完成归集→跨期顺延→同步的业务流程；重建应用容器后数据仍存在；备份可恢复；压测结果记录实际配置、数据量、请求模型、延迟、错误率和资源使用，不把 1000 个账号直接等同为 1000 个并发请求。

## 3. 镜像交付方式

默认提供两个应用镜像，数据库复用官方 PostgreSQL 镜像：

| 交付物 | 内容 |
| --- | --- |
| web 镜像 | 编译后的前端及静态资源服务、/api 代理配置 |
| api 镜像 | NestJS 运行程序、生产依赖、数据库迁移执行入口 |
| 镜像归档 | 可由 docker load 装载的应用镜像归档；附版本与校验信息 |
| compose.yaml | 应用、数据库、网络、持久卷、健康检查及依赖配置 |
| 环境变量示例 | 数据库地址、账号/邮件配置、应用地址等，实际密钥通过部署环境注入 |
| 部署文档 | 构建或装载镜像、初始化、启动、升级、备份恢复、故障排查及版本回退 |
| 构建流程 | GitHub Actions 测试与镜像构建配置；镜像推送目标后续适配 |

数据库数据保存在数据库持久存储及备份中，不打包进应用镜像。镜像归档与运行包会明确说明所需 PostgreSQL 镜像版本；若部署环境不允许拉取外部镜像，可在最终打包时一并归档依赖镜像。

基础构建从第 1 阶段持续验证，第 6 阶段交付经过生产配置与干净环境验证的镜像，而不仅是 Dockerfile。

## 4. 可评审的里程碑

- 阶段 2 后：四层核心在线版，可开始检查业务操作是否符合使用习惯。
- 阶段 4 后：统计、对齐和顺延历史完整，可评审主要业务闭环。
- 阶段 6 后：同步、迁移、移动体验、容量及镜像部署完成，形成正式交付包。

第一至第六阶段已在当前工作目录实施，待 GitHub 仓库提供后对接。用户可以选择逐阶段执行，也可以将相邻阶段合并执行；后续阶段的执行方式由用户决定。
