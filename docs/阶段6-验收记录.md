# 第六阶段：生产镜像、容量与最终交付

测试日期：2026-10-22—23。交付日期：2026-10-23。版本：1.0.0。工作目录：`D:/download/ws-p`。本阶段在本地完成；未发布公网服务或推送镜像，GitHub 仓库尚未提供。

## 功能与体验

- 补齐系统/浅色/深色外观，登录、事项、概览、对齐、历史与对话框使用一致的表面和文本颜色；偏好在重开后保留。
- 手机布局继续使用年度/月度双视图；触控按钮保留至少 44 px 高度，输入字号及日期布局适配 390 px 窗口，未观察到横向溢出。
- 提供 manifest、192/512/maskable 图标和独立窗口声明。Chrome 安装资格检查无错误，已观察到原生安装入口；不将浏览器资格检查冒充所有系统上的实体设备安装。
- 新版等待用户更新，先确认本机写入完成，再激活 service worker；失败时保留当前页面，激活后草稿和主题保留。API 不被 service worker 缓存。
- 数据库恢复标记在完整恢复后更换。浏览器重建正式缓存，保留离线草稿，处理相同数字版本下的恢复冲突及备份之后产生的缓存“幽灵记录”。

## 容量实测

采用全新 Compose 项目、独立数据库及随机测试会话，未写入现有用户数据库。实测 Docker Linux x86_64，可用 16 CPU / 约 7.63 GiB；容器限制为 API 2 CPU / 1 GiB、PostgreSQL 2 CPU / 2 GiB、web 1 CPU / 128 MiB，API 连接池 10。

建立 1000 个账号，每个 4 年度、24 月度、52 周任务、365 日待办，共 445000 条事项，覆盖一年业务日期。常规并发 25；集中读取并发 100；批量顺延并发 10。登录会话为压测专用 SQL 种子，注册、密码、真实 SMTP 和浏览器离线流程另行验证。

| 场景 | 请求数 | P95 | HTTP 错误 |
| --- | ---: | ---: | ---: |
| 全量事项缓存导出 | 1000 | 684 ms | 0 |
| 今日概览 | 1000 | 752 ms | 0 |
| 年度执行 | 1000 | 505 ms | 0 |
| 对齐体检 | 1000 | 723 ms | 0 |
| 100 并发集中读取概览 | 1000 | 1672 ms | 0 |
| 连续自动保存 | 3000 | 462 ms | 0 |
| 离线队列新增回放 | 1000 | 400 ms | 0 |
| 离线队列更新回放 | 3000 | 433 ms | 0 |
| 丢失响应后的同编号重试 | 400 | 307 ms | 0 |
| 批量跨期补偿 | 1000 | 1693 ms | 0 |
| 重复补偿检查 | 1000 | 125 ms | 0 |

合计 14400 次请求，零接口错误。1000 条离线新增均只保留一份，后续版本符合 3 次更新的预期；8000 条旧周期事项完成承接，重复请求没有再次承接。产生 9000 份封存、137000 条封存事项及 8000 条排期历史；数据库约从 162 MiB 增至 388 MiB。

按 15 秒周期的 Docker 采样，API 峰值约 103 MiB、数据库约 424 MiB、web 约 19 MiB；CPU 最高观测约 154% / 218% / 23%（Docker 百分比以单核为 100%，采样值不是持续核数承诺）。原始采样、P50/P95/P99、请求数量、时段和数据库规模见 `artifacts/stage6/capacity.json`。

恢复标记接入后的正式“身份确认→缓存读取”路径另外使用同一 1000 账号数据集，以 25 并发验证 2000 次请求，零错误；P95 分别为 383 ms / 531 ms，结果见 `artifacts/stage6/cache-capacity.json`。它不执行业务变更。

这些是本机 HTTP 回环负载、指定数据量和并发模型的实测，不等于 1000 个同时操作的浏览器、1000 次并发密码登录或客户生产网络的延迟承诺。真实浏览器的 IndexedDB、断网重开、队列、冲突和账号隔离由浏览器回归覆盖；容量脚本中的“离线”场景衡量服务端回放负载。API 仍使用账号全量事项缓存读取，持续增长或更高集中度应按实际监测扩容或增量同步优化。

## 部署与恢复演练

- 原工作台升级前完整备份为 `artifacts/stage6/pre-stage6.dump`；现有用户数据库及持久卷保留，不进入运行包。
- 生产 Compose 在全新项目及数据库卷中启动成功，迁移、API、web、数据库健康。非 root、只读根文件系统、能力限制及资源上限均在该配置中实跑。
- 完整容量库备份恢复到独立空库，账号、四层事项、封存和排期历史逐表内容指纹一致；应用容器重新创建后也一致。
- 目标非空和备份内容被篡改时，恢复工具均拒绝操作。恢复后撤销会话与验证码，轮换客户端恢复标记。
- 仅启动迁移/API/web、连接另一项目 PostgreSQL 的独立数据库模式通过健康检查；没有运行该项目的本地 db 服务。
- 恢复环境完成注册、访客迁移、四层编辑、真实断网重开、重复请求、输入期间上传、版本冲突、清空备份恢复及账号切换的浏览器回归。
- 单独模拟恢复后“事项数字版本未变、内容已经回退”，确认浏览器不会自动上传旧队列；本机草稿保留，缺失缓存记录被移除，可以选择恢复后的云端内容。

## 验证记录与复现

```sh
npm run check
npm run format:check
npm run test:integration
npm run test:browser
npm run test:ui
```

37 项 PostgreSQL / SMTP 集成测试通过，覆盖前五阶段回归和恢复标记接口；浏览器无未捕获异常。浏览器测试使用独立 Chrome 配置，不操作使用者的浏览器。`CHROME_PATH` 可指定 Chrome/Chromium，默认访问 `http://localhost:8080`。

容量脚本只允许 `workbench_capacity` 专用空库，拒绝对既有用户库播种。复现时使用新测试项目与数据库：

```sh
node scripts/prepare-capacity.mjs init
docker compose --env-file .local/stage6-capacity.env -f compose.production.yaml -f compose.capacity.yaml --profile database up -d --wait
node scripts/prepare-capacity.mjs connect
npm run test:capacity
node scripts/cache-capacity.mjs
```

已有 `.local/stage6-capacity.env` 时初始化拒绝覆盖；已有种子库也拒绝重复播种。测试库需明确作为可丢弃环境单独准备，不删除真实用户库来复现。后台顺延在受控压测中关闭，跨期负载由显式请求触发；正常部署默认每 15 秒分批检查最多 50 个账号，访问时补偿继续启用。

## 运行包

运行包目录为 `artifacts/stage6/release-1.0.0/`，包含实际镜像归档、可复现源码、生产 Compose、脱敏配置、备份恢复工具、完整运行文档、来源与校验清单及验证摘要。整体压缩包为 `artifacts/stage6/four-layer-workbench-1.0.0-linux-amd64.tar.gz`，附 SHA-256。

镜像以版本和源代码指纹形成固定标签，OCI revision 与 `release.json` 对应。没有提供 Git 仓库，不伪造提交号；CI 配置包含常规集成、浏览器和手动容量检查，但未声称远端 CI 已执行。最终归档使用实际镜像文件，不只交付 Dockerfile。

归档装载后使用固定镜像标签和 `--pull never`，在新 Compose 项目及新数据库卷中再次启动，证明运行包不依赖现有应用容器或业务数据。校验与启动证据见交付清单和归档旁的 `release-archive-check.json`。

正式域名、HTTPS 证书、SMTP、服务器、镜像仓库仍需客户环境配置；本地演练未替代这些外部环境的最终验证。部署、备份、恢复、日志及回退步骤见 [生产部署与恢复](D:/download/ws-p/docs/生产部署与恢复.md)。
